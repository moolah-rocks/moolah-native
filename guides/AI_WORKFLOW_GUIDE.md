# AI Workflow Guide

Shared build, test, and commit workflow for AI assistants.

## Git Workflow

- `main` is protected and does not accept direct pushes. Every change lands through a pull request.
- Do not edit files on the `main` checkout. Make changes on a feature branch.
- Open the PR with `gh pr create`. Never run `git push origin main`.
- Read-only inspection and investigation can happen on `main` without a branch.

Branch management is assistant-specific: an assistant with dedicated worktree tooling (for example, Claude's `EnterWorktree`/`ExitWorktree`) uses it; any agent without that tooling defaults to `wt` (Worktrunk) to manage worktrees, e.g. `wt switch --create <branch>`. See the assistant's own instruction file for details.

## Commands

Use `just` targets for consistent builds and test runs:

```bash
just
just test
just test TransactionStoreTests
just test TransactionStoreTests/testPayScheduledTransaction
just test-mac TransactionStoreTests AccountStoreTests
just build-mac
just run-mac
just build-ios
just generate
just format
just format-check
```

`Moolah.xcodeproj` is generated by `xcodegen` and gitignored. Never edit `project.pbxproj` directly. Edit `project.yml`, then run `just generate`.

## Test Output

When running tests, capture output in `.agent-tmp/`:

```bash
mkdir -p .agent-tmp
just test 2>&1 | tee .agent-tmp/test-output.txt
```

Use `.agent-tmp/` for temporary agent files. Do not use `/tmp` for repo task output. Use descriptive filenames when running multiple commands, and delete temporary output after inspection when it is no longer useful.

## Pre-Commit

Before committing code:

1. Run `just format`.
2. Run `just format-check` when validating CI formatting.
3. Check compiler warnings. User-code warnings must be fixed; preview macro warnings from `#Preview` can be ignored.
4. Run the relevant tests or build target for the change.
5. Run the required AI reviewer cycle from `guides/AI_ASSISTANT_GUIDE.md` and `guides/AI_REVIEW_GATE_GUIDE.md`.

There is no SwiftLint baseline. Do not add one, do not pass `--baseline`, do not run `swiftlint --write-baseline`, do not silence violations with `// swiftlint:disable` without real justification, and do not raise SwiftLint thresholds to dodge failures.

The project treats warnings as errors (`SWIFT_TREAT_WARNINGS_AS_ERRORS: YES`). Common warning fixes:

- Unused result: assign to `_ =`.
- Variable never mutated: change `var` to `let`.
- Immutable value never used: remove it.
